# Writing sandbox extensions

Work happens in **devices**: one device is a file system plus a disposable instance, shared by every conversation bound to it and their sub-agents. The kernel's sandbox tools (`Bash` / `Read` / `Write` / `Edit` / `Glob` / `Grep` / `Deliver`), attachment sync and `Skill` use it through the kernel's `SandboxService`. `sandbox@2` is a **single-choice, brokered** extension point: a deployment installs only one sandbox extension, and other extensions cannot `requires` it. `@2` replaces `@1` with no overlap; a provider still on `@1` fails to load, and the manifest requires `sdk: "^0.1.0-rc.3"`. For general extension writing see `.agents/skills/writing-extensions`. The kernel side (the `SandboxService` lifecycle, leases, fencing, suspension and destruction, the builtin sandbox tools) is core's: [writing-sandbox-providers in core](https://github.com/capybara-hq/core/tree/main/.agents/skills/writing-sandbox-providers).

Reference implementations:

- `plugins/sandbox-docker`: one container per device plus two named volumes (runc, or gVisor's runsc), reaching Docker only through a socket proxy; the egress allowlist is enforced by a proxy container each sandbox brings along.
- `plugins/sandbox-e2b`: E2B cloud or self-hosted; the paused sandbox is the file system, pause (without memory) for suspension, connect for resume; a hand-written minimal client (the official SDK reads process environment variables and has a module-level connection pool).

The two READMEs spell out the platform sources, every trade-off and the known limitations; write a new implementation at that level of detail.

## Contract: `sandbox@2` (SDK `sandbox.ts`)

```ts
interface SandboxProvider {
  createFileSystem({ name, limits, signal }): Promise<FileSystemHandle>;  // name = cap-device-<deviceId>; idempotent by name
  destroyFileSystem(fs, signal): Promise<void>;           // not being there counts as success
  destroyFileSystemByName(name, signal): Promise<void>;   // no handle: crash mid-create, device deletion, the kernel's legacy cleanup
  create({ name, image?, limits, fileSystem, signal }): Promise<SandboxHandle>;  // an instance attached to the file system
  resume(h, signal): Promise<"resumed" | "gone">;
  suspend(h, signal): Promise<void>;          // files must be kept; an instance that is not there also counts as success
  destroy(h, signal): Promise<void>;          // the instance only, never the files; not being there counts as success
  destroyByName(name, signal): Promise<void>; // the instance only
  killAll(h, signal): Promise<void>;
  readonly concurrentExec: true;              // required: exec / readFile / writeFile / stat may run concurrently on one instance
  killTagged(h, tags, signal): Promise<void>; // required: kill only the exec commands labelled with one of tags
  exec(h, { command, cwd?, env?, timeoutMs, maxOutputBytes, signal, tag, actor }): Promise<ExecResult>;  // actor = { accountId, conversationId }
  readFile(h, path, { maxBytes, signal }): Promise<{ data; truncated } | null>;  // missing or a directory → null
  writeFile(h, path, data, signal): Promise<void>;                               // parent directories are created automatically
  stat(h, path, signal): Promise<{ size; isDir } | null>;
}
```

`glob` / `grep` / `edit` are composed by the kernel from `exec` + `readFile` / `writeFile`; the provider does not implement them. So the image must have GNU `find` (`-print0`) and `grep` (`-rnHIE`, `--include`), `timeout`, `setsid`, `pkill` / `pgrep`.

### File system versus instance

- The **file system** holds the device's files and lives until the device is deleted (Docker: the `-workspace` and `-skills` volumes; E2B: the paused sandbox). The **instance** is the process host attached to it: suspended when idle, destroyed after long disuse, recreated on the next use with the same files. `destroy` / `destroyByName` therefore **keep the files**; only `destroyFileSystem` / `destroyFileSystemByName` remove them (and, in the same call, any instance still using them).
- `createFileSystem` is **idempotent by name**: a second call with the same name returns the existing file system unchanged (the kernel may crash after the provider built it but before it recorded the handle). Limits given to it are fixed at that moment.
- `create` with a file system that no longer exists throws **`FileSystemGoneError`** (duck-typed like `SandboxGoneError`; check with `isFileSystemGoneError`) and **never creates an empty one**; the files are lost and the kernel tells the model and the device page instead of silently starting over. Docker would create empty volumes for missing mounts, so: check that both volumes exist **with their role label** (`dev.capybara.sandbox.role=workspace|skills`) before building anything, and check again after the container is created and before it starts (a removal in the gap leaves Docker-made empty volumes; drop the instance, remove those, then throw). E2B: an E2B-format 404 on connect is `FileSystemGoneError`; 5xx, a bare 404 and a missing access token stay ordinary errors.
- `destroyFileSystemByName` is also what the kernel's one-off legacy cleanup calls with old `cap-<conversationId>` names, so it must remove sandbox@1 layouts too (Docker: the instance of that name, then `<name>-workspace` and `<name>-skills`; E2B: look up running and paused sandboxes by metadata name). Missing resources count as success and a second call succeeds again.
- `image` is optional and reaches only `create`. Without it the provider uses its **published default image**, `ghcr.io/capybara-hq/capybara-sandbox:<plugin version>` (Docker also `capybara-sandbox-egress:<plugin version>` for the egress proxy), resolved in the setup from the manifest version (`providerConfig(config, version = plugin.version)`), never a `latest` tag. Neither an image nor a default is an English error before Docker is touched.
- `exec` takes a required `tag` and an informational `actor` (`{ accountId, conversationId }`); record it for audit at most and never act on it.

### Published images

The two images are built from `plugins/sandbox-docker/image/` and published by `.github/workflows/images.yml` (native amd64 + arm64 builders, a multi-arch tag per image named after the **sandbox-docker version**, only on `main`, only when the tag is missing, so a tag is never rebuilt). Because the e2b plugin uses its own version as the image tag, `.changeset/config.json` keeps both plugins in one `fixed` group: they always release with the same version, and the image they name exists. Never change one plugin's version alone. The workflow's invariants (permissions, digest artifact names that cannot match each other, no `github.event` in `run:`) are asserted by `tools/checks/test/workflows.test.ts`; extend it when you change the workflow. An offline deployment builds the images itself and sets `sandbox.image` and `egressProxyImage` (Docker) or its own `template` (E2B).

### Semantics you must follow

- **Abort**: every method responds to `signal` promptly. Already aborted at call time → reject immediately; aborted in flight → end as soon as possible with the abort reason. The kernel relies on this to stop when a lease is lost, the run is aborted or times out; without it you may operate on the instance alongside a new lease holder. **An aborted `exec` must kill the command and its child processes**, not merely stop waiting; an `exec` aborted after the command started resolves normally with `{ exitCode: null, timedOut: false }` (with the output so far) and does not reject. A timeout resolves `timedOut: true, exitCode: null`.
- **gone versus ordinary errors**: when the instance is **definitely** gone on the provider's side (container deleted, E2B sandbox expired), `exec` / `readFile` / `writeFile` / `stat` / `killAll` throw `SandboxGoneError` and `resume` returns `"gone"`. The kernel then recreates the instance on the same file system, retries once, and the model sees a restarted notice (processes are gone, files are kept). Losing the file system is `FileSystemGoneError`, not this. If the instance is only temporarily unreachable (401, 5xx, network errors, a bare 404 from a proxy), throw an **ordinary error**; otherwise one network blip wipes the user's files. Check with `isSandboxGoneError` (duck typing). E2B treats only E2B-format 404s (`{code: 404, …}`) as gone; failing to obtain the envd access token is also gone (better to fail than to send a request without the token). On E2B the instance is the file system's own sandbox, so the kernel's new instance reconnects the same sandbox id and fails the same way: the device stays unusable until its files are reset or it is recreated (see the E2B README).
- **Auto-start**: when the instance exists but is stopped / paused (host or daemon restart, a suspension that stopped it before the kernel recorded `suspended`, a manual `docker pause`), `exec` / `readFile` / `writeFile` / `stat` / `killAll` first start it the way `resume` does, then proceed without error. The kernel trusts only the `running` it recorded itself.
- **Command time limit inside the sandbox**: besides stopping the command on the provider side at `timeoutMs`, the command itself runs inside the sandbox through `timeout -s KILL <timeoutMs + a few seconds>`. When a kernel replica crashes its timer disappears and disconnecting does not end the command; this limit keeps it from running indefinitely alongside the next holder's commands.
- **killAll**: kill every command started through `exec` that is still running (SIGKILL by process group and session); background processes in a new session are not guaranteed. **Implement it for the case where no other holder can be running a command**: the kernel calls it only under the exclusive lease and right after recovering from `suspended`; crashed holders are killed by tag, never with `killAll`. The fallbacks below also end live siblings' commands, which is why it is that restricted. When the killing exec cannot even start (process table exhausted), Docker falls back to `restart?t=0` and E2B to pause (without memory) + a `connect {memory: false}` cold start; both log a warn (Docker through the `log` passed to `createDockerSandbox`, the extension's `ctx.log`) and return normally.
- **Concurrent use (`concurrentExec`, `killTagged`, `tag`; all required)**: every session of a device and their sub-agents share one instance, so the kernel calls `exec` / `readFile` / `writeFile` / `stat` concurrently on one instance. Those methods must then be safe concurrently, and **auto-start must be idempotent under concurrent calls** (Docker's `start` on a running container answers 304, E2B `connect` on a running sandbox only extends its timeout). Every `exec` gets the holder's `tag` (`SANDBOX_TAG_RE`, `^[a-z0-9-]{1,64}$`, checked by the provider before it goes near a command line): label the command with it (the official providers name the control file `/tmp/.capybara-exec-<tag>-<uuid>`), and implement `killTagged(h, tags)` to kill only those commands' process trees, matching the whole tag: `capybara-exec /tmp/[.]capybara-exec-<tag>-<uuid>( |$)` with the UUID's exact shape, because a tag may be a prefix of another (`ab` of `ab-cd`). An aborted or timed-out `exec` still kills only its own command. A provider that does not declare `concurrentExec: true` and implement `killTagged` fails to load. Concurrent commands share the sandbox's pids and memory limits; say so in the README.
- **Same-name replacement**: Docker: `create` first deletes an old instance of the same name (never its file system), then builds (E2B has no separate instance: `create` reconnects the file system's sandbox) (the kernel may exit after the provider built it but before it recorded the handle). Implement `destroyByName` and `destroyFileSystemByName` too: without a handle the kernel cleans up by `cap-device-<deviceId>` (device deletion, test cleanup) and legacy `cap-<conversationId>`.
- **Output**: `maxOutputBytes` is the **combined** limit on stdout + stderr; excess is discarded and `truncated` set; truncation backs off to a full UTF-8 character boundary.
- **`/skills` is read-only**: mounted read-only for the sandbox user (or owned by root with 0755); `writeFile("/skills/…")` is written by the provider as root and must not be redirected by a symlink the sandbox user placed. The kernel's protection checks only the path string; the real defense is the provider. Skill files have no executable bit (the model runs them through an interpreter, `sh /skills/x/run.sh`).
- **File operations resolve as the sandbox user**: permissions and symlinks resolve as the non-root user (Docker runs small `head` / `stat` scripts in the container; E2B's upload endpoint opens the target as root, so upload to a root-only staging directory first and write the target with `runuser -u sandbox`). Never write volumes as root through the daemon.
- Paths have passed the kernel's `validateSandboxPath` (only `/workspace`, `/skills`, `/tmp`); the working directory is `/workspace`, attachments are in `/workspace/attachments/<conversation>/`.

### Limits and egress (`SandboxLimits`)

- `tier` / `egress` / `allowHosts` / `cpu` / `memoryMb` are the values **in effect for the org**: the kernel applies the org's egress setting (never more open than the deployment) and a super admin's per-org cpu / memory overrides before calling `create`. The provider just enforces what `create` receives and never reads org settings. A provider that cannot size each sandbox (E2B: the template decides) states in its README that org-level cpu / memory overrides do not take effect; deployers use different templates instead.
- `cpu` / `memoryMb` / `diskMb` / `tier` / `egress` / `allowHosts` **take effect only where the resource is made**: `cpu` / `memoryMb` / `tier` / `egress` / `allowHosts` at `create` (E2B: at `createFileSystem`, because the template and the sandbox exist from then on), `diskMb` at `createFileSystem`. Declare where with `limitsApplyAt: "instance" | "fileSystem"` (absent = `"instance"`; Docker `"instance"`, E2B `"fileSystem"`): the kernel records new limits only when they are really in force. Existing file systems and instances (including resumed ones) keep their settings until recreated, except a change of **tier or egress mode**, which the kernel applies on the next use through the optional **`update(h, limits, signal)`** under the exclusive lease: return `"updated"` when the running instance now enforces the new limits, `"recreate"` when it must be destroyed and recreated on the same files (also what a thrown `update` or a missing `update` leads to). Never answer `"updated"` with a state that a later rebuild (resume, auto-start) could widen: Docker records the create-time mode and hosts in container labels, changes only the egress proxy in place when the new proxy allows at least that, and removes a half-made proxy when `update` fails. Changes of `allowHosts`, cpu, memory and disk alone keep the old rule (they reach instances created afterwards); say all this in the README. When an item cannot be done, say so in the README (Docker's default local volume driver does not limit `diskMb`; E2B's cpu / memory / disk come from the template).
- `tier` (`strict` | `dev` | `open`; treat an absent one as `strict`) is the effective sandbox tier; `allowHosts` is already final (the kernel merges the dev hosts `D` into it for `dev`), so providers never read `devHosts`. The network per tier: `egress: "none"` is no network in **every** tier (the kill switch); `allowlist` is `allowHosts` (Docker: its egress proxy in `MODE=strict` for `strict`, 443 / 80 and HTTP only, and in `MODE=dev` above it, `CONNECT` to any port of an allowed host plus SOCKS5 on 1080, with `ALL_PROXY` / `GRPC_PROXY` / `GIT_SSH_COMMAND` set in the container; E2B: `allowOut` on 80 / 443); `open` egress comes only with the `open` tier. `dev` and `open` also get development room (Docker: `/dev/shm` of `min(1 GiB, memoryMb / 4)`); everything else (non-root user, read-only root, dropped capabilities, pids limit) is the same in every tier.
- `egress`:
  - `none`: loopback only.
  - `allowlist` (default): only `allowHosts` (`validateAllowHost` already rejects IP literals, single-label names and `.local` / `.internal`; `*.example.com` matches subdomains, not the domain itself).
  - `open`: governed by the provider's deployment config **`openEgress: "off" | "proxy" | "direct"`** (default `"proxy"`; it replaced `allowOpenEgress`, which now fails the strict schema with a pointer to `openEgress`). `off`: `create` / `update` (E2B: `createFileSystem` / `update`) with open fails with an English error naming `openEgress`. Docker `proxy`: the egress proxy in `MODE=open` (any public host and port; private, loopback, link-local and metadata addresses still refused); Docker `direct`: the shared bridge (reaches the host and intranet; trusted environments only). E2B: both mean `allow_internet_access: true`. New extensions offer the same setting.
- **The allowlist does not prevent data exfiltration** to allowlisted hosts (`git push` to github.com, publishing packages). The README must say so and recommend `sandboxToolPolicy: ask` and / or `sandboxEgress: none` for sensitive orgs.
- A provider that cannot allow by domain name must **refuse, or degrade to `none` with a warning**, never silently open up (E2B self-hosted `domainAllowlist: false`). Where it can but more weakly, write it in the README (E2B looks only at Host / SNI and does not verify the destination IP).

## E2B mapping

E2B has no separate volume, so the paused sandbox is the file system (spec `docs/superpowers/specs/2026-11-07-environments-design.md` §5.3 in core):

- `createFileSystem`: look up a sandbox with the metadata name (`capybara-sandbox-name`, running and paused) and return it if present; otherwise ensure the template, `POST /v2/sandboxes` with `autoPause: true`, `autoPauseMemory: false`, `secure: true` and the egress mapping, then pause it **without memory** (`pause {memory: false}`). The handle is the E2B sandbox id.
- `create`: `connect` (retry the 409), return the same id. The `image` and `limits` arguments are ignored because both were fixed at `createFileSystem`; a custom image therefore means your own template and the `template` setting.
- `suspend` / `destroy`: pause without memory (404 and 409 count as success). `destroyByName`: pauses only the **running** sandboxes of that name. `destroyFileSystem*`: `DELETE` (by name across running and paused, so legacy names too).
- Pausing without memory drops processes and keeps files; `killAll`'s fallback is a pause plus `connect {memory: false}`.
- **Template**: when the `template` setting is empty, the plugin builds one from the published image under the alias `capybara-sandbox-<tag>` (the image tag lower-cased, characters outside `[a-z0-9-]` replaced by `-`): look up `GET /templates/aliases/<alias>`, else `POST /v3/templates`, `POST /v2/templates/<t>/builds/<b>` with `fromImage`, then **poll** the build status until `ready` (an `error` status or a failed trigger surfaces its reason; the result is memoised per provider instance, shared by concurrent callers, a failure is not kept, and the wait follows the extension's lifetime signal). An existing alias that cannot start a sandbox (E2B answers 404) is rebuilt once.
- **The alias must be non-public and owned by this team.** Refuse a lookup or build response with `public !== false` and map 403/409 to one English error that tells the admin to set `template` to their own; never build over a foreign alias.

## What the kernel's `SandboxService` owns

The extension implements only primitives. **No scheduling, timers or state tables in the extension.** What the kernel guarantees:

- **State and lazy creation**: the kernel records each device's file system and instance (status, handle, provider) in PG; `createFileSystem` runs when the device is made and `create` on the first sandbox use.
- **Leases**: commands take shared leases (up to `sandbox.maxConcurrentCommands`); every lifecycle change (create, rebuild after `gone`, `resume`, `suspend`, `destroy`, `killAll` after resume) runs alone under the exclusive lease. Leases expire and are fenced, so a holder that lost its lease has its signal aborted and its state writes refused. Two replicas using a device for the first time build only one; several holders hitting `gone` together rebuild once.
- **Takeover of crashed holders**: their commands are killed with `killTagged` by the next holder; whatever escapes ends at the in-sandbox time limit.
- **Kernel file writes are serialized per path**; shell commands are not.
- **Suspension** of the instance after `suspendAfterIdleMinutes` (default 10) idle or `maxRunningMinutes` (default 120) running; **destruction of the instance** after `destroyAfterInactiveDays` (default 7). Both keep the files. The file system is removed only with its device (or a files reset). A suspended instance is resumed on next use; `gone` or destroyed recreates the instance on the same files with a notice. A lost file system (`FileSystemGoneError`) is reported, never silently rebuilt. A one-off kernel job calls `destroyByName` and `destroyFileSystemByName` for every old per-conversation `cap-<conversationId>` instance. Switching providers leaks old instances while the old extension is unloaded.
- **Time limits**: per command `sandbox.limits.maxCommandSeconds` (default 7200; `Bash` defaults to 120 s), tightened to the owning run's remaining time.

## Security

- **Docker's socket proxy** (core's `docker/sandbox-proxy/haproxy.cfg`; the plugin's tests start it from the copy `plugins/sandbox-docker/test/sandbox-proxy/haproxy.cfg`): allows only the endpoints the extension uses, containers / volumes only by names starting with `cap-`, and rejects request bodies by regex for privileged mode, `Binds`, `CapAdd`, non-ASCII keys (Go folds key names by Unicode, `Bindſ` = `Binds`) and so on. **This is only a backstop; the main defense is network position**: anything that can reach the proxy can nearly control Docker. **Never publish the proxy on any host address (127.0.0.1 included)** in production; put it only on the kernel's internal network and never attach sandboxes to that network. The dev compose publishes it on `127.0.0.1:2375` for the local machine only; then never set `openEgress: "direct"` (a sandbox on the bridge can reach the host loopback through `host.docker.internal`). The extension reaches Docker only through `endpoint` and never mounts `docker.sock`.
- **Container hardening**: commands run as non-root (uid 1000); PID 1 runs as root with `CapDrop: ALL` (the sandbox user cannot stop the container), `no-new-privileges`, a read-only root filesystem, `PidsLimit`, private IPC, `/tmp` a tmpfs.
- **The egress proxy blocks DNS rebinding**: checking only the hostname cannot stop `10.0.0.1.nip.io`. The proxy resolves first, and **every resolved IP** must not be private, loopback, link-local (169.254.169.254 included), CGNAT, ULA, multicast or reserved (IPv4-mapped / NAT64 / 6to4 judged by the embedded IPv4), then connects to the checked IP with no second resolution. HTTPS goes through CONNECT, only ports 443 / 80 in `strict` (any port of an allowed host in `dev`, any public host and port in `open`); the SOCKS5 listener of `dev` / `open` applies the same checks. New egress implementations follow this standard.
- Logs and errors carry no secrets (E2B API key, envd token) and no other orgs' ids.

## Tests

- **Docker extension**: `buildTestImages` (tagged by the content of the build context, built once per run under a lock and kept for later runs), `startSocketProxy` (a real HAProxy) and `cleanupTestResources` (by label) in `plugins/sandbox-docker/test/docker-env.ts`; without Docker (or with `CAPYBARA_TEST_NO_DOCKER=1`) the group is skipped, and runsc cases run only when the daemon has runsc registered. Test-only options (extra labels, `egressTestHosts`) go through the second parameter of `createDockerSandbox`; the extension config is strict and cannot set them. A change to the socket proxy rules comes with a violating case against the real proxy (proving it is rejected), and the proxy config must stay identical to core's `docker/sandbox-proxy/haproxy.cfg`.
- **E2B extension**: `startFakeE2B` from `@capybara-hq/testing` (control plane + envd; commands really run in a local temp directory); the real-E2B `test/live` runs only when `CAPYBARA_TEST_E2B_API_KEY` is set (the template is optional and auto-built when unset; `CAPYBARA_TEST_E2B_TEMPLATE` pins one; optional `CAPYBARA_TEST_E2B_API_URL` / `CAPYBARA_TEST_E2B_DOMAIN` for self-hosted), and the file header lists "assumptions that can only be confirmed in a real environment", to check one by one on the first run. Keep keys in an env file outside the repository and never print them.
- **Dual-replica through a real kernel**: `plugins/sandbox-docker/test/sandbox-artifacts.dual.test.ts` (real Docker; takeover after killing the executing replica, recovery after suspension; it reads the device's `cap-device-<id>` instance and volumes); `@capybara-hq/testing` exports the kernel texts and keys to assert on (`SANDBOX_STARTED_NOTICE`, `SANDBOX_RESTARTED_NOTICE`, `SANDBOX_LOCK_TTL_MS`, `SANDBOX_SUSPEND_JOB`). Concurrent holders: `plugins/sandbox-docker/test/concurrent.test.ts`.
- Every provider covers at least: gone versus ordinary errors, abort (before the call / in flight), a timeout killing the whole process group, auto-start, killAll, same-name replacement, **destroy keeps files** (a new instance sees them), **`FileSystemGoneError` on a removed file system** (and no empty file system made), **`destroyFileSystemByName` removes legacy names** (`cap-<conversationId>` layouts, a second call succeeds), `createFileSystem` idempotent by name, a `/skills` write through a symlink being rejected, the egress modes per tier (and `update`, if implemented), and output truncation at a UTF-8 boundary.
- Run from the repository root: `pnpm exec vitest run plugins/sandbox-docker`.
