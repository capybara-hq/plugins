# Writing device providers

Work happens in **devices**: one device is a file system plus a disposable instance, shared by every conversation bound to it and their sub-agents. The kernel's sandbox tools (`Bash` / `Read` / `Write` / `Edit` / `Glob` / `Grep` / `Deliver` / `FetchAttachment`) and `Skill` use it through the kernel. `device-provider@1` is a **multi, brokered, org-scoped** extension point: several device providers coexist in a deployment (which ones an org can use is the catalog's scope of each plugin), every device is bound to the provider that made it, and other extensions cannot `requires` it. It replaces `sandbox@2` with no overlap and no alias: the kernel refuses a plugin that provides an unknown point such as `sandbox@2`, and devices made by the old `sandbox-docker` / `sandbox-e2b` read as unavailable. The manifest requires `sdk: "^0.1.0-rc.51"`. For general extension writing see `.agents/skills/writing-extensions`. The kernel side (device lifecycle, leases, fencing, suspension and destruction, the builtin sandbox tools) is core's: [writing-device-providers in core](https://github.com/capybara-hq/core/tree/main/.agents/skills/writing-device-providers); the design is core's `docs/superpowers/specs/2026-11-21-device-provider-design.md`.

Reference implementations:

- `plugins/device-docker`: one container per device plus two named volumes (runc, or gVisor's runsc), reaching Docker only through a socket proxy; the egress allowlist is enforced by a proxy container each sandbox brings along.
- `plugins/device-e2b`: E2B cloud or self-hosted; the paused sandbox is the file system, pause (without memory) for suspension, connect for resume; a hand-written minimal client (the official SDK reads process environment variables and has a module-level connection pool).

The two READMEs spell out the platform sources, every trade-off and the known limitations; write a new implementation at that level of detail.

## Contract: `device-provider@1` (SDK `device-provider.ts`)

```ts
interface DeviceProvider {
  readonly networkAllowlist: true;            // required: the provider enforces a host allowlist (checked at load)
  report(device: { deviceId, orgId, handle }, signal): Promise<DeviceReport>;  // shown on the device page
  createFileSystem({ name, limits, signal }): Promise<FileSystemHandle>;  // name = cap-device-<deviceId>; idempotent by name
  destroyFileSystem(fs, signal): Promise<void>;           // not being there counts as success
  destroyFileSystemByName(name, signal): Promise<void>;   // no handle: crash mid-create, device deletion, the kernel's legacy cleanup
  create({ name, image?, limits, fileSystem, signal }): Promise<SandboxHandle>;  // an instance attached to the file system
  resume(h, signal): Promise<"resumed" | "gone">;
  suspend(h, signal): Promise<void>;          // files must be kept; an instance that is not there also counts as success
  destroy(h, signal): Promise<void>;          // the instance only, never the files; not being there counts as success
  destroyByName(name, signal): Promise<void>; // the instance only
  killAll(h, signal): Promise<void>;
  readonly concurrentExec: true;              // required: exec / readFile / writeFile / stat may run concurrently on one instance
  killTagged(h, tags, signal): Promise<void>; // required: kill only the exec commands labelled with one of tags
  exec(h, { command, cwd?, env?, timeoutMs, maxOutputBytes, signal, tag, actor }): Promise<ExecResult>;  // actor = { accountId, conversationId }
  readFile(h, path, { maxBytes, signal }): Promise<{ data; truncated } | null>;  // missing or a directory → null
  writeFile(h, path, data, signal): Promise<void>;                               // parent directories are created automatically
  stat(h, path, signal): Promise<{ size; isDir } | null>;
  list?(h, path, { limit, signal }): Promise<{ entries: { name; isDir }[]; truncated } | null>;  // optional: projects
  scan?(h, base, { signal }): Promise<{ path; suggestedName }[]>;                            // optional: projects
}
```

### The device report and the connection guide

- **`report(device, signal)`** answers `{ revision, description: { en, zh? }, home, limits, reset }` (`parseDeviceReport` and `DEVICE_REPORT_LIMITS` in the SDK). It is shown to people only, never used for enforcement; capability facts stay in `permissionSupport`. `revision` is opaque and must change whenever anything else in the report changes (the official providers join the plugin version, the runtime or template, the instance id and, for Docker, the instance's limits). `description` is one line on what the device is; `home` is `null` for an instance-boundary provider (the project picker starts from the workspace); `limits` are what the provider applies on top (Docker: the cpu / memory / disk the container was created with, none without an instance; E2B: none, the template decides); `reset: true` where the files can be reset. `report` must not create or start anything. `changeHint` (optional `{ en, zh? }`, at most `DEVICE_REPORT_LIMITS.changeHintChars`) says in the provider's words who changes the device's limits and how: the device page shows it under the limits and the kernel appends its English text to refusals that cite the report (an escalated call not allowed now, a network the device side keeps on the allowlist), so state the mechanism (device-local: the machine's owner, `capybara-device ceiling set -c <device id> …` on that machine; Docker / E2B: the super admin's settings and the device's network setting). A support whose closed crossing is kept closed by the machine's owner rather than the provider says so with `limitedBy: { outsideSandbox?: "owner", openPublic?: "owner" }` (only on a closed crossing): the kernel then names the owner layer instead of the provider.
- **`networkAllowlist: true`** is a static declaration: a ceiling may hold a device to `allowlist`, so a provider that cannot enforce one does not load. A provider that degrades an allowlist to no network (E2B self-hosted `domainAllowlist: false`) still declares it: closed, never open.
- **Guide**: one setup guide at the place `device-connection` (`setupGuides: [{ id: "connect", place: "device-connection" }]`, `guides/connect.md` and `connect.zh.md`; audience member, variables `publicUrl`, `orgId`, `orgName`, `pluginName`). For a provider without dial-in it is short: what the device is, that the platform's super admin set it up, then "Give it a name, then create it." The zh copy says 平台 / 设备 / 智能体.

`glob` / `grep` / `edit` are composed by the kernel from `exec` + `readFile` / `writeFile`; the provider does not implement them. So the image must have GNU `find` (`-print0`) and `grep` (`-rnHIE`, `--include`), `timeout`, `setsid`, `pkill` / `pgrep`.

### File system versus instance

- The **file system** holds the device's files and lives until the device is deleted (Docker: the `-workspace` and `-skills` volumes; E2B: the paused sandbox). The **instance** is the process host attached to it: suspended when idle, destroyed after long disuse, recreated on the next use with the same files. `destroy` / `destroyByName` therefore **keep the files**; only `destroyFileSystem` / `destroyFileSystemByName` remove them (and, in the same call, any instance still using them).
- `createFileSystem` is **idempotent by name**: a second call with the same name returns the existing file system unchanged (the kernel may crash after the provider built it but before it recorded the handle). Limits given to it are fixed at that moment.
- `create` with a file system that no longer exists throws **`FileSystemGoneError`** (duck-typed like `SandboxGoneError`; check with `isFileSystemGoneError`) and **never creates an empty one**; the files are lost and the kernel tells the model and the device page instead of silently starting over. Docker would create empty volumes for missing mounts, so: check that both volumes exist **with their role label** (`dev.capybara.sandbox.role=workspace|skills`) before building anything, and check again after the container is created and before it starts (a removal in the gap leaves Docker-made empty volumes; drop the instance, remove those, then throw). E2B: an E2B-format 404 on connect is `FileSystemGoneError`; 5xx, a bare 404 and a missing access token stay ordinary errors.
- `destroyFileSystemByName` is also what the kernel's one-off legacy cleanup calls with old `cap-<conversationId>` names, so it must remove sandbox@1 layouts too (Docker: the instance of that name, then `<name>-workspace` and `<name>-skills`; E2B: look up running and paused sandboxes by metadata name). Missing resources count as success and a second call succeeds again.
- `image` is optional and reaches only `create`. Without it the provider uses its **published default image**, `ghcr.io/capybara-hq/capybara-sandbox:<plugin version>` (Docker also `capybara-sandbox-egress:<plugin version>` for the egress proxy), resolved in the setup from the manifest version (`providerConfig(config, version = plugin.version)`), never a `latest` tag. Neither an image nor a default is an English error before Docker is touched.
- `exec` takes a required `tag` and an informational `actor` (`{ accountId, conversationId }`); record it for audit at most and never act on it.

### Published images

The two images are built from `plugins/device-docker/image/` and published by `.github/workflows/images.yml` (native amd64 + arm64 builders, a multi-arch tag per image named after the **device-docker version**, only on `main`, only when the tag is missing, so a tag is never rebuilt). Because the e2b plugin uses its own version as the image tag, `.changeset/config.json` keeps both plugins in one `fixed` group: they always release with the same version, and the image they name exists. Never change one plugin's version alone. The workflow's invariants (permissions, digest artifact names that cannot match each other, no `github.event` in `run:`) are asserted by `tools/checks/test/workflows.test.ts`; extend it when you change the workflow. An offline deployment builds the images itself and sets `sandbox.image` and `egressProxyImage` (Docker) or its own `template` (E2B).

### Semantics you must follow

- **Abort**: every method responds to `signal` promptly. Already aborted at call time → reject immediately; aborted in flight → end as soon as possible with the abort reason. The kernel relies on this to stop when a lease is lost, the run is aborted or times out; without it you may operate on the instance alongside a new lease holder. **An aborted `exec` must kill the command and its child processes**, not merely stop waiting; an `exec` aborted after the command started resolves normally with `{ exitCode: null, timedOut: false }` (with the output so far) and does not reject. A timeout resolves `timedOut: true, exitCode: null`.
- **gone versus ordinary errors**: when the instance is **definitely** gone on the provider's side (container deleted, E2B sandbox expired), `exec` / `readFile` / `writeFile` / `stat` / `killAll` throw `SandboxGoneError` and `resume` returns `"gone"`. The kernel then recreates the instance on the same file system, retries once, and the model sees a restarted notice (processes are gone, files are kept). Losing the file system is `FileSystemGoneError`, not this. If the instance is only temporarily unreachable (401, 5xx, network errors, a bare 404 from a proxy), throw an **ordinary error**; otherwise one network blip wipes the user's files. Check with `isSandboxGoneError` (duck typing). E2B treats only E2B-format 404s (`{code: 404, …}`) as gone; failing to obtain the envd access token is also gone (better to fail than to send a request without the token). On E2B the instance is the file system's own sandbox, so the kernel's new instance reconnects the same sandbox id and fails the same way: the device stays unusable until its files are reset or it is recreated (see the E2B README).
- **Auto-start**: when the instance exists but is stopped / paused (host or daemon restart, a suspension that stopped it before the kernel recorded `suspended`, a manual `docker pause`), `exec` / `readFile` / `writeFile` / `stat` / `killAll` first start it the way `resume` does, then proceed without error. The kernel trusts only the `running` it recorded itself.
- **Command time limit inside the sandbox**: besides stopping the command on the provider side at `timeoutMs`, the command itself runs inside the sandbox through `timeout -s KILL <timeoutMs + a few seconds>`. When a kernel replica crashes its timer disappears and disconnecting does not end the command; this limit keeps it from running indefinitely alongside the next holder's commands. The wrapper never looks up `timeout`, `setsid` or its own tools on the command's PATH (the published image's PATH starts with `/workspace/.cache/npm-global/bin`, which the sandbox user can write): the official providers start `setsid` by absolute path or through a lookup on the system PATH (`SYSTEM_PATH`, root-owned directories), resolve `timeout` on it inside the wrapper, and give every other provider-run script (kill scripts, file scripts, root writes) `PATH=SYSTEM_PATH`; only the user's command keeps the image's PATH (plugins#106). Tests plant fake tools in that directory and check the limit, the kills and the root writes are unaffected.
- **killAll**: kill every command started through `exec` that is still running (SIGKILL by process group and session); background processes in a new session are not guaranteed. **Implement it for the case where no other holder can be running a command**: the kernel calls it only under the exclusive lease and right after recovering from `suspended`; crashed holders are killed by tag, never with `killAll`. The fallbacks below also end live siblings' commands, which is why it is that restricted. When the killing exec cannot even start (process table exhausted), Docker falls back to `restart?t=0` and E2B to pause (without memory) + a `connect {memory: false}` cold start; both log a warn (Docker through the `log` passed to `createDockerSandbox`, the extension's `ctx.log`) and return normally.
- **Concurrent use (`concurrentExec`, `killTagged`, `tag`; all required)**: every session of a device and their sub-agents share one instance, so the kernel calls `exec` / `readFile` / `writeFile` / `stat` concurrently on one instance. Those methods must then be safe concurrently, and **auto-start must be idempotent under concurrent calls** (Docker's `start` on a running container answers 304, E2B `connect` on a running sandbox only extends its timeout). Every `exec` gets the holder's `tag` (`SANDBOX_TAG_RE`, `^[a-z0-9-]{1,64}$`, checked by the provider before it goes near a command line): label the command with it (the official providers name the control file `/tmp/.capybara-exec-<tag>-<uuid>`), and implement `killTagged(h, tags)` to kill only those commands' process trees, matching the whole tag: `capybara-exec /tmp/[.]capybara-exec-<tag>-<uuid>( |$)` with the UUID's exact shape, because a tag may be a prefix of another (`ab` of `ab-cd`). An aborted or timed-out `exec` still kills only its own command. A provider that does not declare `concurrentExec: true` and implement `killTagged` fails to load. Concurrent commands share the sandbox's pids and memory limits; say so in the README.
- **Same-name replacement**: Docker: `create` first deletes an old instance of the same name (never its file system), then builds (E2B has no separate instance: `create` reconnects the file system's sandbox) (the kernel may exit after the provider built it but before it recorded the handle). Implement `destroyByName` and `destroyFileSystemByName` too: without a handle the kernel cleans up by `cap-device-<deviceId>` (device deletion, test cleanup) and legacy `cap-<conversationId>`.
- **Output**: `maxOutputBytes` is the **combined** limit on stdout + stderr; excess is discarded and `truncated` set; truncation backs off to a full UTF-8 character boundary.
- **`/skills` is read-only**: mounted read-only for the sandbox user (or owned by root with 0755); `writeFile("/skills/…")` is written by the provider as root and must not be redirected by a symlink the sandbox user placed. The kernel's protection checks only the path string; the real defense is the provider. Skill files have no executable bit (the model runs them through an interpreter, `sh /skills/x/run.sh`).
- **File operations resolve as the sandbox user**: permissions and symlinks resolve as the non-root user (Docker runs small `head` / `stat` scripts in the container; E2B's upload endpoint opens the target as root, so upload to a root-only staging directory first and write the target with `runuser -u sandbox`). Never write volumes as root through the daemon.
- Paths have passed the kernel's checks: on a cloud device the instance is the sandbox, so file calls may reach any clean absolute path inside it. A provider checks only the shape (`validateSandboxPathShape`: absolute, no `..` or empty segments), never root membership. The working directory is `/workspace`, `FetchAttachment` copies an attachment to `/workspace/attachments/<conversation>/` on demand (attachments are not synced into the device by themselves).

### Projects: `list` and `scan` (optional)

A provider with both offers projects on its devices (core spec 2026-11-14 project root); without them its conversations stay in free mode. The doc comments in the SDK's `sandbox.ts` are normative; core's local device is the reference (`packages/device/src/exec/listing.ts`, and `exec/docker.ts`'s `LIST_SCRIPT` for a container). Both read **inside the instance**, never the volume or the sandbox from outside, so links resolve as the instance sees them.

- **Reachable area**: on a cloud device the container's `/workspace` (spec §4.2; the kernel scopes a cloud device's projects to it). A path outside it, lexically or after resolving links, throws (a policy refusal); in `list`, a link whose target leaves it is `isDir: false`.
- **`list`**: entries sorted by UTF-16 code unit, at most `limit` (`truncated` when there are more), never `.` / `..`; `isDir` follows links (stat semantics; dangling = false). `null` only for a missing path inside the area (a path below a file and a dangling link too); containment is checked on the resolved path before anything is looked up, so a missing path below a link out throws instead of telling whether it exists; a file or an unreadable directory throws.
- **`scan`**: `base` and the directories at most `MAX_DEVICE_SCAN_DEPTH` levels below it holding a `.git` entry or an `AGENTS.md` file; breadth-first, each level in code-unit order of path, `base` the first visit, at most `MAX_DEVICE_SCAN_DIRS` visits (an unreadable directory counts and is skipped); no link following, no hidden directories, exactly `DEVICE_SCAN_SKIPPED_DIRS` (any depth) and `DEVICE_SCAN_SKIPPED_BASE_DIRS` (under `base`); a hit does not stop the descent; a directory whose basename fails `isDeviceProjectName` is walked but never returned; candidates sorted by path, the first `MAX_DEVICE_SCAN_RESULTS`. Missing `base` → `[]`; a `base` that is a file, unreadable or outside the workspace throws.
- **The official providers** run one `python3 -I -c` script (`src/listing.ts`, duplicated byte for byte in both plugins, asserted by `tools/checks/test/sandbox-listing.test.ts`; it follows the rules of core's local device docker mode, it is not the same script) as the sandbox user under `timeout -s KILL 30` with `PATH=/usr/local/bin:/usr/bin:/bin` (the image's PATH starts with a directory the sandbox user can write), the path as argv (never interpolated into code). The provider normalizes the path first (`.` / `..`, a trailing slash); the script reports scan paths relative to the base and the provider joins them to the normalized base. The image must carry python3 and timeout (named in the Dockerfile's conventions); a missing one (exit 127) and the time limit (exit 137) are clear errors. Gone, auto-start and abort follow the file calls (an abort returns at once; the read-only script ends at its time limit at worst). Tests: `test/list-scan.test.ts` in each plugin, the case list of core's device tests.

### Limits and network (`SandboxLimits`)

- `network` / `cpu` / `memoryMb` are the values **in effect for the device**: the kernel applies the platform and org network ceilings, the org default and the device's own network choice (never more open than the deployment; a device host list only narrows the org's) and a super admin's per-org cpu / memory overrides before calling `create`. The provider just enforces what `create` receives and never reads org settings. A provider that cannot size each sandbox (E2B: the template decides) states in its README that org-level cpu / memory overrides do not take effect; deployers use different templates instead.
- `cpu` / `memoryMb` / `diskMb` / `network` **take effect only where the resource is made**: `cpu` / `memoryMb` / `network` at `create` (E2B: at `createFileSystem`, because the template and the sandbox exist from then on), `diskMb` at `createFileSystem`. Declare where with `limitsApplyAt: "instance" | "fileSystem"` (absent = `"instance"`; Docker `"instance"`, E2B `"fileSystem"`): the kernel records new limits only when they are really in force. Existing file systems and instances (including resumed ones) keep their settings until recreated, except a change of the **network**, which the kernel applies on the next use through the optional **`update(h, limits, signal)`** under the exclusive lease: return `"updated"` when the running instance now enforces the new limits, `"recreate"` when it must be destroyed and recreated on the same files (also what a thrown `update` or a missing `update` leads to). Never answer `"updated"` with a state that a later rebuild (resume, auto-start) could widen, and answer `"updated"` for a **narrowing** only once no connection to a removed host survives and no new one can open (otherwise `"recreate"` or throw). Docker applies allowlist to a non-empty allowlist (wider, narrower or both) **in place** on instances with the egress control label: `docker exec` hands the proxy the new list (and the current `deniedCidrs`) on its control socket (a tmpfs Unix socket only the proxy container reaches); the proxy writes it to the instance's config volume `<name>-egress-conf`, swaps it, closes every registered connection the new list does not cover (registered at admission, before resolution; a connection still connecting re-checks before it is spliced) and only then answers with the list's digest, which `update` compares with the digest of what it sent. The container labels keep the create-time list, which after a narrowing is wider than the list in force, so a lost proxy is rebuilt only from the config volume; without it `resume` answers `gone` and `update` `"recreate"` (never a rebuild from the labels), and the permission operations read the list in force from the proxy (`control status`). A change of kind (allowlist to open-public too, and the empty list, `NetworkMode: none`) recreates so the labels name the kind; instances of an earlier version (no control label) keep the proxy swap for a list that keeps every labelled host and recreate otherwise. cpu, memory and disk alone keep the old rule (they reach instances created afterwards); say all this in the README. When an item cannot be done, say so in the README (Docker's default local volume driver does not limit `diskMb`; E2B's cpu / memory / disk come from the template).
- **The limits carry no `mode`** (core approval-only profiles design): on a cloud provider the instance is the sandbox, and its network is every operation's sandbox network. A new allowlist host needs a change of the device's list: a host cannot be granted per call, since the instance network covers the whole instance.
- **Operation contract on an instance-boundary device**: `permissionSupport` reports support v2 `{ version: 2, boundary: "instance", restricted: null, network: { openPublic, allowlist, perOperationHosts: false }, outsideSandbox: false, background }`, the network flags matching what the provider enforces (Docker: `openPublic` off under `refuseOpenNetwork`; E2B: `allowlist` off under `domainAllowlist: false`). The kernel's scope there is `filesystem: scoped` with `projectRoot` (the conversation's working directory, or null in free mode) and `writeRoots` holding `/` (and the working root), under every profile; read roots are no longer sent (what a sandboxed operation may read is the provider's rule; for an instance-boundary provider the whole instance is readable); the provider runs it on its ordinary exec and file paths behind the durable admission (consume record, `revokeOperation`, exact background supervision). It refuses before any effect, with `SandboxPermissionUnsupportedError` and never widened, the escalated pair (`device` filesystem with the `environment` network: an instance has no outside) and any narrower filesystem grant (restricted filters). An unusable staged runtime offers nothing (network flags and `background` false) and names the reason. **Staged SDK runtime files** (`native-files.py`, `linux-sandbox.py`): an image provider (device-docker) stages the SDK's `SANDBOX_RUNTIME_SOURCE.current` bytes as of the SDK it was restaged from (`STAGED_SDK_DIGESTS`, `SHA256SUMS`), and checks each staged copy against the **host** SDK's `SANDBOX_RUNTIME_SOURCE.accepted` (the kernel's SDK: its staged set, its current bytes and at most one previous revision), never one exact digest, so an instance of an earlier image stays usable while the kernel's SDK accepts what it staged; operations `expect` only the files the agent runs. A host SDK without `accepted` makes support unavailable. A provider that uploads the files at runtime (device-e2b) stages the host SDK's `files`. A change to these files follows core's three steps ("Changing the SDK runtime sources" in core's tools/checks/README.md): core ships the new bytes in `current`, then this repository restages from the released SDK and raises its SDK range, then core promotes `current` to `files` and moves `marketplace.commit` with the device-docker pin.
- `network` (`{ kind: "open-public" | "allowlist", hosts }`) is the network the instance must enforce. `open-public`: any public host on any port; the provider must refuse the SDK's closed address classes (`OPEN_PUBLIC_DENIED_CIDRS` / `classifyAddress`: private, CGNAT, ULA, link-local and metadata, loopback, multicast, broadcast, unspecified, NAT64 and reserved) by **resolved IP** (DNS rebinding); an egress proxy that resolves names itself re-resolves a fake-IP answer (198.18.0.0/15) through DNS-over-HTTPS per `SANDBOX_FAKE_IP_DNS` and never dials the fake address (Docker's `proxy.mjs` keeps checked copies of both constants). `allowlist`: only `hosts` (`validateAllowHost` already rejects IP literals, single-label names and `.local` / `.internal`; `*.example.com` matches subdomains, not the domain itself); an empty list reaches nothing — the platform's kill switch arrives as `allowlist` with `hosts: []`, there is no `none` kind (Docker maps it to `NetworkMode: none` with no proxy, the same profile otherwise). A kernel that predates the contract sends neither field: treat that as an empty allowlist (the safe direction) or refuse the create, **never as open-public**. `validateAllowHost` and the shape rules the proxy applies are the standard; new egress implementations follow it.
- A provider that cannot enforce the open network's private-address block must **refuse `open-public`** (fail closed), never silently open. A deployment setting such as Docker's **`refuseOpenNetwork`** (default `false`) makes `create` / `update` throw an English error naming the setting, and an existing instance whose labels say open-public answers `gone` on resume / auto-start so the kernel recreates it under the rule. Say in the README how an operator turns it off or narrows the org's network. An exposure no setting of the provider can close, under every network kind (E2B's metadata service, MMDS), is not a reason to refuse `open-public` (refusing removes nothing): map it and state the residual in the README and the manifest (core spec 2026-11-15 auto mode hardening, D1). Docker also refuses `168.63.129.16` and the deployment's own ranges (`deniedCidrs`).
- **The allowlist does not prevent data exfiltration** to allowlisted hosts (`git push` to github.com, publishing packages). The README must say so and recommend `sandboxToolPolicy: ask` and / or `sandboxEgress: none` for sensitive orgs.
- A provider that cannot allow by domain name must **refuse, or degrade to an empty allowlist with a warning**, never silently open up (E2B self-hosted `domainAllowlist: false`). Where it can but more weakly, write it in the README (E2B looks only at Host / SNI and does not verify the destination IP).

## E2B mapping

E2B has no separate volume, so the paused sandbox is the file system (spec `docs/superpowers/specs/2026-11-07-environments-design.md` §5.3 in core):

- `createFileSystem`: look up a sandbox with the metadata name (`capybara-sandbox-name`, running and paused) and return it if present; otherwise ensure the template, `POST /v2/sandboxes` with `autoPause: true`, `autoPauseMemory: false`, `secure: true` and the egress mapping, then pause it **without memory** (`pause {memory: false}`). The handle is the E2B sandbox id.
- `create`: `connect` (retry the 409), return the same id. The `image` and `limits` arguments are ignored because both were fixed at `createFileSystem`; a custom image therefore means your own template and the `template` setting.
- `suspend` / `destroy`: pause without memory (404 and 409 count as success). `destroyByName`: pauses only the **running** sandboxes of that name. `destroyFileSystem*`: `DELETE` (by name across running and paused, so legacy names too).
- Pausing without memory drops processes and keeps files; `killAll`'s fallback is a pause plus `connect {memory: false}`.
- **Template**: when the `template` setting is empty, the plugin builds one from the published image under the alias `capybara-sandbox-<tag>` (the image tag lower-cased, characters outside `[a-z0-9-]` replaced by `-`): look up `GET /templates/aliases/<alias>`, else `POST /v3/templates`, `POST /v2/templates/<t>/builds/<b>` with `fromImage`, then **poll** the build status until `ready` (an `error` status or a failed trigger surfaces its reason; the result is memoised per provider instance, shared by concurrent callers, a failure is not kept, and the wait follows the extension's lifetime signal). An existing alias that cannot start a sandbox (E2B answers 404) is rebuilt once.
- **The alias must be non-public and owned by this team.** Refuse a lookup or build response with `public !== false` and map 403/409 to one English error that tells the admin to set `template` to their own; never build over a foreign alias.

## What the kernel's `SandboxService` owns

The extension implements only primitives. **No scheduling, timers or state tables in the extension.** What the kernel guarantees:

- **State and lazy creation**: the kernel records each device's file system and instance (status, handle, provider) in PG; `createFileSystem` runs when the device is made and `create` on the first sandbox use.
- **Leases**: commands take shared leases (up to `sandbox.maxConcurrentCommands`); every lifecycle change (create, rebuild after `gone`, `resume`, `suspend`, `destroy`, `killAll` after resume) runs alone under the exclusive lease. Leases expire and are fenced, so a holder that lost its lease has its signal aborted and its state writes refused. Two replicas using a device for the first time build only one; several holders hitting `gone` together rebuild once.
- **Takeover of crashed holders**: their commands are killed with `killTagged` by the next holder; whatever escapes ends at the in-sandbox time limit.
- **Kernel file writes are serialized per path**; shell commands are not.
- **Suspension** of the instance after `suspendAfterIdleMinutes` (default 10) idle or `maxRunningMinutes` (default 120) running; **destruction of the instance** after `destroyAfterInactiveDays` (default 7). Both keep the files. The file system is removed only with its device (or a files reset). A suspended instance is resumed on next use; `gone` or destroyed recreates the instance on the same files with a notice. A lost file system (`FileSystemGoneError`) is reported, never silently rebuilt. A one-off kernel job calls `destroyByName` and `destroyFileSystemByName` for every old per-conversation `cap-<conversationId>` instance. Switching providers leaks old instances while the old extension is unloaded.
- **Time limits**: per command `sandbox.limits.maxCommandSeconds` (default 7200; `Bash` defaults to 120 s), tightened to the owning run's remaining time.

## Security

- **Docker's socket proxy** (core's `docker/sandbox-proxy/haproxy.cfg`; the plugin's tests start it from the copy `plugins/device-docker/test/sandbox-proxy/haproxy.cfg`): allows only the endpoints the extension uses, containers / volumes only by names starting with `cap-`, and rejects request bodies by regex for privileged mode, `Binds`, `CapAdd`, non-ASCII keys (Go folds key names by Unicode, `Bindſ` = `Binds`) and so on. **This is only a backstop; the main defense is network position**: anything that can reach the proxy can nearly control Docker. **Never publish the proxy on any host address (127.0.0.1 included)** in production; put it only on the kernel's internal network and never attach sandboxes to that network. The dev compose publishes it on `127.0.0.1:2375` for the local machine only; a sandbox reaches the network only through its egress proxy, which refuses loopback and private addresses. The extension reaches Docker only through `endpoint` and never mounts `docker.sock`.
- **Container hardening**: commands run as non-root (uid 1000); PID 1 runs as root with `CapDrop: ALL` (the sandbox user cannot stop the container), `no-new-privileges`, a read-only root filesystem, `PidsLimit`, private IPC, `/tmp` a tmpfs.
- **The egress proxy blocks DNS rebinding**: checking only the hostname cannot stop `10.0.0.1.nip.io`. The proxy resolves first, and **every resolved IP** must not be private, loopback, link-local (169.254.169.254 included), CGNAT, ULA, multicast or reserved (IPv4-mapped / NAT64 / 6to4 judged by the embedded IPv4), then connects to the checked IP with no second resolution. HTTPS goes through CONNECT on any port (the host list constrains hosts, not ports); the SOCKS5 listener applies the same checks. New egress implementations follow this standard.
- Logs and errors carry no secrets (E2B API key, envd token) and no other orgs' ids.
